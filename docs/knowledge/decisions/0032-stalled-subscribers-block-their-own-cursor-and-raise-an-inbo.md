# Stalled Subscribers block their own cursor and raise an inbox item; no DLQ

Context: when a Subscriber's handler throws on event N, three failure-handling shapes were considered: (1) block the cursor (preserve at-least-once, but no operator surface), (2) skip + log (silent state corruption — exactly the staleness class this design exists to kill), (3) per-event dead-letter queue (advance past poison events into a separate table). Decision: each Subscriber's cursor blocks on the failing event_id and the handler retries on every wake. After K=3 consecutive failures on the same event_id, a subscriber-stalled inbox item is raised with structured {subscriberId, eventId, eventName, lastError}. Cursor stays blocked; one stalled Subscriber does not block others (cursors are independent). Recovery emits subscriber.unstalled which auto-closes the inbox item via the ADR-0027 Invalidator path. Why: Mars events are not independent — task.terminal for a blocker is a prerequisite for task.unblocked on its dependents; a DLQ that advances past a poison terminal would silently strand every downstream task in blocked forever. Block-the-cursor preserves correctness; the inbox item provides the operator surface (per CLAUDE.md, the inbox is the single human-facing work surface). Trade-off accepted: a permanently-broken Subscriber halts forever until an operator intervenes; visibility comes from the inbox item, not from the system silently routing around the problem.
