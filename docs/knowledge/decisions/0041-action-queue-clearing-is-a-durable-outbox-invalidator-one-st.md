# Action-queue clearing is a durable-outbox Invalidator; one status-writer emit, build-guard-enforced

Context: task->Action-queue clearing was done inline at the updateTask chokepoint with a best-effort subscriber backstop; raw-SQL status writers (unblockTask, dropTask, slicer, fix-task/blocker/main-dirty blocked-writes) bypassed it, stranding rows and orphaning dismissals (measured: 13 orphaned task-dismissals + stale open failed rows). This implements the already-accepted ADR-0027/0028/0030/0031/0032 design end-to-end: every task lifecycle event is appended to the outbox in the SAME transaction as the status write, and the Invalidator (the alert-dismisser subscriber) is now the SOLE closer of Action-queue rows + dismissals, consuming task.terminal{done|dropped|purged} (never failed, ADR-0028) plus task.queued/unblocked eviction. dropTask emits task.terminal{purged} BEFORE deleting the row so a removed task still closes its rows. Decision/trade-off: rather than wait on the ADR-0021 TaskStore migration (only partially landed) to own the emit at the data layer, every status change routes through one writer and a build-guard vitest (db-writes-eventful) fails CI on any raw 'UPDATE tasks SET status' / 'DELETE FROM tasks' outside a small allowlist of emitting files. This makes the single-writer property structural (a planted bypass turns the test red) rather than convention-policed; the emit relocates into TaskStore for free once ADR-0021 completes. Also: kept the live table names events/subscribers rather than renaming to ADR-0030's literal outbox_events/outbox_subscriptions — pure churn that moves no behaviour; the rename is a separate mechanical change if ever wanted.
