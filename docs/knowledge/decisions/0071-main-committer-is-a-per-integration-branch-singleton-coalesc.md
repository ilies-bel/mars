# Main committer is a per-integration-branch singleton; coalesce by branch not file-set hash

Context: dirty-main recovery keyed coalescing on dirtyMainHash=sha256(git status), treating each distinct file-set as an independent dirty state deserving its own committer. Because main is one physical working tree with one dirty state, this fanned out into concurrent committers and, once a committer failed (failed committers were excluded from coalescing), a re-spawn storm — evidenced by ~60 committers sharing one hash spawned every ~2min. Decision: the Main committer is a singleton per integration branch. A dirty-main source attaches to the one live (non-done, non-failed) committer for the branch; a fresh committer spawns ONLY when none is live, and on spawn it re-parents every still-blocked dirty-main source (including those orphaned on failed committers) onto itself. Failed committers are frozen as-is (status, action-queue row, historical edges retained) and never collect new waiters. dirtyMainHash and episodeHash are removed from the recovery payload; the singleton makes both obsolete. The worktree+stash execution shape is kept (no in-place commit). Why: the anti-storm property now rests entirely on the singleton invariant (attach-never-spawn-when-live) rather than on a per-episode hash guard; this supersedes the dedup model in ADR-0040's slice-F.2 clarification. Cost: the old 'keep dependents blocked when main is still dirty' guard in releaseMainCommitterDependents is removed, superseded by re-parenting onto the singleton — safe only because a re-parented source ATTACHES to the one live committer instead of spawning its own.

Enforcement (migration 0008, schema version 0036): the singleton invariant is now enforced at the database level by a partial unique index `uq_tasks_active_main_committer` on `tasks((recovery_payload::jsonb ->> 'recipe'), (recovery_payload::jsonb ->> 'integrationBranch'))` WHERE `kind = 'fix' AND status IN ACTIVE_COMMITTER_STATUSES`. Done/failed/dropped committers fall outside the index so a fresh committer can spawn on the same branch once the previous one settles. The application layer catches the Postgres 23505 unique violation from a concurrent INSERT, re-resolves the active committer, and attaches to it — making `spawnOrAttachMainCommitter` optimistic and race-safe without any explicit lock. Pre-existing duplicate active committers (if any) are reaped to 'failed' by the migration DO block before the index is created. The invariant is therefore both structurally enforced (cannot be violated by a concurrent INSERT) and handled gracefully in application code (loser attaches rather than crashing).
