# Subscribers are code-declared with durable cursors; bootstrap defaults to tail

Context: Subscribers (Outbox consumers) could be DB-driven rows, code-declared, or in-memory only. Bootstrap policy for a fresh Subscriber could replay history from event_id=0 or tail from MAX(event_id). Decision: Subscribers are code-declared at daemon boot with stable string ids; INSERT OR IGNORE seeds one row per id in outbox_subscriptions(subscriber_id, last_acked_event_id). Code is the source of truth for what Subscribers exist; the DB is the source of truth for how far each has gotten. Each Subscriber declares a bootstrap mode (replay | tail); default is tail, with the initial last_acked_event_id set to (SELECT COALESCE(MAX(event_id), 0) FROM outbox_events) so a fresh cursor sees only future events. Why: DB-driven Subscribers create a silent-drop footgun (row without handler = silent skip; handler without row = silent drop until manual insert with no obvious starting point); in-memory cursors lose durability across restarts, defeating the whole design. Defaulting to tail prevents replay storms when the cutover lands (existing event consumers are already up to date with the world; they don't want to relive history). Trade-off accepted: adding a Subscriber requires a daemon restart; acceptable for a single-binary local daemon.
