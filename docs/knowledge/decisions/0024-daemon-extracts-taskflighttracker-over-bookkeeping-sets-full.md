# Daemon extracts TaskFlightTracker over bookkeeping sets; full SlotPool seam rejected

Context: orchestrator/src/mastra/daemon/server.ts is a 1465-LOC module whose `startDaemon` closure captures a Map of in-flight Slots, two Pending sets (triage, implement), two Claimed sets (triage, implement -- the dispatch-storm fix at server.ts:230-236), a Record<DispatchKind,Semaphore> with five named slots mapping onto three logical pools (glossary-write and adr-add share one structuredWriteSem because they contend on the same downstream merge lock), the drain logic, three per-kind dispatcher closures (dispatchTriage, dispatchImplement, dispatchRefine), and ~20 RPC handlers that bus.emit('task.queued') after DB writes. The Semaphore primitives (makeSem, acquire, release, setSemLimit) are already top-level module exports at server.ts:62-112 and already tested by daemon/__tests__/sem-reload.test.ts. ADR-0012 explicitly mandates daemon-side semaphores ('daemon semaphores ... must live in the consumer, not the engine'); ADR-0014's strangle has not started -- packages/workflow/ is README-only with no engine code yet.

Three SlotPool seam designs were produced and compared by depth, locality, and seam placement:

- State+Drain (pool owns sems Record + dispatch-storm state + drain; dispatcher closures stay in startDaemon as injected callbacks; pickImplement runs as a caller-supplied predicate so DB knowledge stays out of the pool).
- Full Ownership (pool owns state, drain, AND a typed DispatcherMap naming triage/implement/refine/glossaryWrite/adrAdd; bus subscription moves inside the pool; every Task enters dispatch through one of five submit* methods).
- Skeptic (drop the SlotPool framing; counter-propose either no structural change plus a __test__ factory, or a narrower TaskFlightTracker over just inFlight + pending + claimed + the bookkeeping predicates).

Decision: extract a TaskFlightTracker module owning the four bookkeeping collections (inFlight, pendingTriage, pendingImplement, claimedTriage, claimedImplement) and their predicates (isInFlight, isClaimed, claim, unclaim, trackInFlight returning the release closure, enqueuePending, drainPending, inFlightCount, inFlightSnapshot). The dispatch-storm-prevention invariant -- 'for every taskId, at most one Slot in inFlight ∪ claimed{Triage,Implement} holds it at any instant; claim runs BEFORE await acquire(sem) and clears AFTER trackInFlight commits, covering the await-acquire gap' -- becomes the seam's named, type-documented property. Sems (the Record<DispatchKind,Semaphore>), drain, the per-kind dispatcher closures, and the bus.on/bus.emit glue stay in startDaemon. The structuredWriteSem shared-pool grouping stays as today: a 6-line constant with one footnote comment; not seam-grade. RPC handlers that read in-flight state (status, kill) go through tracker.inFlightSnapshot()/inFlightKind(); the reload-config handler keeps calling the existing top-level setSemLimit per kind.

Two alternative seam shapes were considered and rejected with load-bearing reasons (recorded so future architecture reviews do not re-suggest them):

- Full SlotPool over state + drain + (optionally) dispatchers: rejected on three grounds. (1) The two-adapter rule fails: the codebase has one real adapter (production), one fake-for-test (which the rule explicitly does not count as seam-justifying -- it is a fake-for-testability), and one speculative ADR-0014 'in-house engine' adapter whose contract cannot be designed against today because packages/workflow/ is empty and ADR-0012 already keeps semaphores daemon-side anyway. (2) The deletion test for a full SlotPool concentrates nothing new: the Semaphore primitives are already top-level, so wrapping them is a rename, not a depth gain; meanwhile the drain() body co-mingles three concerns -- semaphore admission, blocker SQL re-checks (hasIncompleteBlockers), and status re-checks (getTask + status filter) -- so a pool that 'owns drain' either drags the queue + blocker layers across its seam (a larger leak than the one it would plug) or splits the invariant via a pickImplement callback (which State+Drain does and openly admits as 'the awkward picker'). (3) The Full Ownership variant additionally bakes Mars Workflow signatures into the pool's type (triage/implement/refine/glossaryWrite/adrAdd), which ADR-0014's engine-dispatch axis would then have to thread through -- the opposite of the engine-agnostic property the pool was supposed to preserve.

- Do nothing structural; add a __test__ factory that exposes the closure for unit tests: rejected as too small -- the dispatch-storm invariant has a load-bearing name (server.ts:230-236 documents it as a bug-fix) and deserves a typed module surface, not a back-door test handle. The narrower TaskFlightTracker keeps the concentration win (the named invariant) without the rest of the SlotPool's speculative coupling.

Why: the actual concentration win is the dispatch-storm invariant, which is flight-tracker-shaped, not pool-shaped. Naming it on a typed module surface (rather than as a comment on a closure) makes the bug-fix structural -- future contributors cannot accidentally bypass it by ordering claim/await wrong, because the trackInFlight return value forces the release-after-commit lifecycle. The strangle-readiness argument for a full SlotPool is speculative (no counterparty code exists) and partially contradicted by ADR-0012 (semaphores stay daemon-side anyway).

Cost: the structuredWriteSem shared-pool grouping invariant ('glossary-write and adr-add map to one Semaphore') stays as today -- a comment on a 6-line construction site, not a type-system property. The ~20 bus.emit('task.queued') call sites in RPC handlers remain a place future ops could bypass the tracker by emit-then-direct-dispatch; the AGENTS.md rule about not doing that stays a convention enforced in review, not by the type system (a property the Full Ownership SlotPool would have given us, at the cost of the speculative coupling). If ADR-0014's strangle eventually produces a workflow engine whose dispatch shape changes the daemon's pool model, a SlotPool seam at that point will be designed against a real counterparty contract rather than guessed -- this ADR explicitly does not preclude one later, it only refuses to build one now.
