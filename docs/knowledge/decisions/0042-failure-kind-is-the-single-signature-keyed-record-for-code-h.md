# Failure kind is the single signature-keyed record for code, human reason, recipe, and actions; supersedes ADR-0035 keying

Context: failure metadata was split across three drifting layers — a code-keyed failure-reason catalog (built-in.ts) bundling userMessage+availableActions, an errorKind-id-keyed registry (error-kinds.ts, ADR-0035) bundling recoveryActions, and a signature-keyed humanization+classification layer (failure-signature.ts) bundling errorClassRules+causeSentencesBySignature. The inbox resolver re-grepped the raw failure string via failureReasonStringToCode instead of using the structured failingStep, collapsing most failures to 'unknown' even when the step and cause were already known. Decision: collapse into ONE record, the Failure kind, keyed by the failure signature <failingStep>/<error-class>, bundling { signature, humanReason, recipe, actions }. The signature is the key because it is the only one of the three keyings that captures substep granularity and because recovery recipes (ADR-0002) already bind to it. failureReasonStringToCode and the parallel code-keyed catalog are deleted; the daemon HTTP layer (ADR-0035) serves Failure kinds keyed by signature instead of ErrorKind ids. Why: one source of truth removes the drift that produced the 'unknown' epidemic and lets code, human reason, and actions be authored together. This supersedes ADR-0035's ErrorKind-id keying while keeping its invariant (daemon is sole writer; UI renders served descriptors). Trade-off: a real re-key touching ADR-0002/0035 seams over the smaller bridge fix, chosen because the duplication was the root defect.
