# Slicer sizing is a prompt-nudge, not a hard size gate

Context: coder runs have a 150k context budget (watchdog kills at 150k, 50k below the 200k window) and an oversized task burns a full run before being killed and recovered. Decision: the slicer prompt instructs the model to estimate each slice's coder-context cost (files touched + steps, against ~150k) and split hot slices before emitting — a reasoning-only nudge that shapes the slice list and never appears in the JSON output, with blockedBy wired between dependent halves on a split. We deliberately did NOT add a token-estimate field on TaskSpec, a dispatch-time size guard, or a recovery re-slice. Why: consistent with ADR-0037 (run-to-natural-completion over pre-emptive kill machinery); the existing 150k watchdog + single recovery remains the sole back-stop. The nudge reduces how often the back-stop fires; it does not replace it. A future reader should not 'upgrade' this into a hard enforcement gate.
