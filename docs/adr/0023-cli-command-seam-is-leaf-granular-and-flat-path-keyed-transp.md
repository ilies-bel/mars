# CLI Command seam is leaf-granular and flat path-keyed; transport is injected, not a Command taxonomy

Context: orchestrator/src/cli.ts is a single ~2030-line main() (file ~2929 lines) implementing ~28 top-level commands as a flat if (cmd === 'x') ladder, ~9 of which carry their own internal subcommand ladders. There are 110 process.exit() calls and ~63 dynamic await import() reaching into ./mastra/daemon/client (19x), ./mastra/proposals (16x), ./mastra/queue (11x), ./mastra/author. The module's interface is main(): Promise<void> -- a maximally shallow seam: ~2030 lines of implementation behind a zero-argument function, with no command independently nameable or testable (the only way to exercise a command today is to spawn the binary). Deletion test: removing main() makes the 28 command behaviours, arg parsing, and 110 exit policies reappear with no home -- complexity concentrates, so the work is real, but ownership is fully diffuse.

The axis of variation that makes a Command seam real (not indirection) was examined: testability has two genuine adapters (production argv path vs in-process test path with injected TaskStore(:memory:) and injected daemon-client, asserting on a returned result instead of process.exit). A second proposed axis -- transport (local read vs daemon-routed mutation) -- was investigated and found to vary PER-SUBCOMMAND, not per-command (e.g. `glossary set`/`remove` are daemon-routed while `glossary list`/`show` are local; `task add` is daemon-routed while `task list` is local; `show` mixes local reads within one subcommand). Modeling transport as a command-level taxonomy (LocalCommand vs DaemonRoutedCommand) would therefore shatter cohesive commands across the taxonomy and is a false seam.

Decision:
1. The CLI gains a Command seam whose unit is the LEAF -- each invocable path ('task add', 'glossary set', 'where') is one Command, registered by its full path in a flat path-keyed registry. The 'task'/'idea'/'glossary' grouping is computed routing (group by path[0] for help/discovery), not an object and not a unit.
2. The Command interface is `run(args, deps) -> CommandResult{code, value?}`. No command calls process.exit; the 110 exits collapse to one mapping site per adapter (production maps code->exit, test asserts on code/value). Commands never import subsystems directly; capabilities arrive via injected deps: TaskStore, a daemon-client, ctx, and out/err sinks.
3. Transport is an injected dependency (the already-existing ./mastra/daemon/client seam), never a Command taxonomy.
4. Pass-through commands ('where', 'list') call injected deps.store directly rather than re-importing query modules; 'mars list' becomes a thin alias delegating to the 'task list' projection so there is one formatter, not two.
5. Shared per-flag parsing (--priority, --type, --blocked-by) ships as exported pure helpers (cli/args.ts); the group-level invariant "every <group> * leaf rejects unknown flags" is enforced by one registry-iterating test.

Two alternative granularities were designed and rejected with load-bearing reasons (recorded so future architecture reviews do not re-suggest them):

- Flat (one unit per top-level command; subcommand ladders stay inside run()): rejected because it leaves an un-seamed second dispatch layer inside the ~9 ladder-bearing commands -- exactly the commands with the most logic and the most process.exit calls -- so a typo'd subcommand fails only at runtime and `task add` is not independently testable. That defeats the stated purpose of the seam (each command testable in-process).

- Recursive composite (one uniform Command interface at every depth via a composite() helper): rejected by its own deletion test -- flattening the recursion to a path-keyed registry leaves CommandResult, injected deps, and the test adapter unchanged, proving the recursion hides nothing. Real CLI depth is fixed at 2 ('task add'), so the uniform tree pays interface ceremony on ~50 leaves to abstract a depth that never grows. Its INTERFACE (Command{path,summary,usage,run}) is adopted; its recursive ASSEMBLY is not.

Why: the seam's leverage is the run()->CommandResult shape plus injected deps (this is what makes the in-process test adapter possible and collapses the 110 exits and ~63 dynamic imports), not the registry topology. Leaf granularity is the only one of the three that delivers in-process testability for every command including the logic-heavy ladder-bearing ones. Keeping transport injected (point 3) preserves command cohesion and reuses the existing daemon-client seam rather than inventing a parallel abstraction the code's structure does not support.

Cost: the registry has ~50-60 entries and ~50-60 small files; total line count rises (the 2030-line main() becomes ~60 leaf files plus a thin router) -- the improvement is locality and testability, not size. Group-level concerns (shared flag validation, "all task * reject unknown flags") lose a natural single home and are paid for explicitly by exported arg helpers and a registry-level test (points 4-5). Trivial leaves ('where', 'ui', 'watch') pay the full Command ceremony for little intrinsic benefit; this is accepted so the router stays a pure prefix match with zero bypass branches. This work depends on the TaskStore seam landing first (deps.store must be the concrete injected store, not a speculative interface).
