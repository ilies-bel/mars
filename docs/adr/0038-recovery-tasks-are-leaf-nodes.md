# Recovery tasks are leaf nodes in the task graph

Context: CLAUDE.md already states "a recovery task is itself non-recoverable: if it fails for any reason — the same failure, a different one, or a watchdog kill — the origin goes to `failed` with one actionable inbox item and the operator resolves it explicitly". That rule prevents origin → recovery → recovery chains, but it is silent on the other two ways a recovery task could grow children in the graph: being declared a blocker of another task, or having its own blockers waited on. The blocker-cascade (`task_blockers` junction, `onBlockerTaskCompleted`, `recoverBlockedTasks`) does not currently care whether either endpoint of an edge is a recovery task — it just walks edges. That gap is the only thing keeping "recovery is a leaf" from being a structural invariant rather than a per-failure rule.

Decision: recovery tasks are leaf nodes in the task graph. They cannot have blockers, cannot be blocked by anything, and cannot themselves be recovered. The blocker-cascade does not recurse through them. There is at most one recovery layer between an origin failure and the operator's inbox. Combined with the existing "exactly one recovery attempt per origin failure" rule from CLAUDE.md, this pins the failure topology to a fixed shape: origin → optional recovery → operator, with no other edges allowed at the recovery node.

Why: the recovery task is the orchestrator's last automatic shot at a failure. Letting it acquire blockers (or be blocked) would invent a second level of "wait for something else before the safety net runs", which is exactly the kind of indirection the one-shot-recovery rule was written to forbid. Letting it be recovered would re-open the same regression by another name — the blocker-cascade chains could grow arbitrarily long while the operator's inbox stayed silent. Keeping recovery as a structural leaf means there is exactly one place in the graph where a failure stops being the orchestrator's problem and starts being the operator's, and that boundary is the same shape every time.

Cost: a single leaf rule generalises three carve-outs (cannot recover, cannot block, cannot be blocked) and must be enforced in three places — the blocker-insertion path, the cascade walker, and the recovery-spawn path. The blocker-cascade walker no longer needs to recurse through "what if this blocker is itself a recovery" branches; it stops the moment it hits a recovery task and the operator sees the original origin failure verbatim. A coder that genuinely wants to bounce a recovery off another task has no escape hatch — they must either fix the work in-band or fail and let the operator resolve via the inbox.

Consequences (enforcement TODOs — code lands in slice F, the `main-commiter` slice that first triggers a recovery task under the new failure model):

- The `task_blockers` insertion path (`store.addBlockers`, `mars block`, `mars task add --blocked-by`) must reject any edge whose either endpoint is a recovery task with a typed error. The check belongs in the store so every entry point (workflow, CLI, daemon RPC) shares one guard.
- `onBlockerTaskCompleted`'s cascade — the daemon hook that flips dependents from `blocked` to `queued` — does not recurse through a recovery task. A recovery completing unblocks only the tasks that were blocked on it directly; no transitive walk past that node.
- The recovery-spawn path must refuse to spawn a recovery for a task that is itself a recovery. The "one recovery per origin failure" budget from CLAUDE.md is the existing guard; this ADR pins the structural shape that makes the budget meaningful (no recovery-of-recovery, by either route).
- `mars unblock <id>` and the inbox's daemon-killed resolution flow assume the leaf invariant when they re-queue work — a recovery task that ends up in `failed` is the operator's call, never the orchestrator's. No code change there, but the invariant is now a documented assumption rather than incidental behaviour.

Clarification (folded in during slice F.2 after the F.1 enforcement landed): the leaf-node rule forbids recovery tasks from having blockers and from being recovered. The single exception is the origin → recovery edge written by the recovery-spawn path (`upsertFixTask`, plus its slice-F.2 dedup sibling `attachToExistingFixTask` and the equivalent insert inside `spawnOrAttachMainCommitter`), which is how a recovery is structurally attached to its origin. This edge is reciprocal (the origin is "blocked-by" the recovery; the recovery has no further blockers) and bounded (`handleTaskFailureWithFixTask` prevents fix-of-fix chains). The blocker-cascade walker still does not recurse through the recovery side of that edge — completion of a recovery unblocks only the origin(s) directly attached, never anything transitively beyond.

This ADR documents the invariant. Code enforcement of the invariant is out of scope for this slice (slice B unifies the trace surface and pins the design); it lands in slice F alongside the first recovery-task-spawning failure code under the reworked failure model. The CLAUDE.md / AGENTS.md updates that propagate this rule into the routing guidance land with slice F as well.
