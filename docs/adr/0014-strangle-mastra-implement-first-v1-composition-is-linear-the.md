# Strangle Mastra implement-first; v1 composition is linear .then only

Context: ADR 0012 commits to replacing Mastra with an in-house, domain-agnostic workflow engine, but does not say which named pipeline migrates first or how rich the v1 composition surface is. Seven named pipelines run on Mastra today (implement, verify, merge, recovery, slicer, linker, sweeper). Migrating them atomically would be a big-bang rewrite with no proving ground; migrating them in an undefined order risks picking a pipeline that does not exercise the engine's load-bearing surface. Separately, every existing pipeline is a linear chain — none branches, forks, loops, or fans out — so the v1 DSL only needs .then to cover today's reality.

Decision: the engine strangles Mastra one pipeline at a time, starting with the implement pipeline. Implement is the load-bearing pipeline (worktree → coder → verify-on-exit → merge), exercises the agent runtime, durable resume, child-logger lineage, and tag-to-Workflow resolution end-to-end, and is the pipeline operators watch most closely — so success on implement is the strongest signal that the engine is ready for the rest. While implement runs on the in-house engine, the remaining six pipelines stay on Mastra; the daemon dispatches to either engine depending on which Workflow id the tag-plus-type resolves to. A follow-up PRD sweeps the remaining pipelines across once implement has been stable in production.

The v1 composition surface is pinned to linear .then chaining only. createWorkflow({...}).then(step).then(step).commit() is the entire DSL. Branching, parallel, foreach, dountil, and dowhile are explicitly out of scope and will be added when a real Workflow demands one of them — not preemptively. Sub-workflow composition (one Workflow embedding another) is likewise deferred; cross-pipeline hierarchy continues to use the existing originId fan-out across peer Tasks.

Why: strangling implement-first front-loads the risk on the pipeline that matters most and gives the engine a real production workload to prove itself against before the sweep. Pinning v1 to .then keeps the engine surface honest — every primitive we ship has a Workflow that needs it — and prevents the engine from ossifying around speculative shapes. Both choices keep the migration reversible: if implement on the in-house engine misbehaves, the daemon can dispatch it back to Mastra by flipping the tag mapping, and no other pipeline is affected.

Cost: Mastra and the in-house engine coexist for the duration of the strangle, which means the daemon carries dispatch logic for two engines, the orchestrator imports both, and operators must mentally model that a Task's engine depends on its tag. Linear-only composition will require an ADR amendment the first time a real Workflow needs branching or parallelism; the amendment is expected, not a surprise. Both costs are explicitly preferred to the alternatives — big-bang migration and speculative DSL — because they preserve optionality.
