# Error-kind registry is the single source of truth for recovery actions; UI drives them over daemon HTTP, daemon stays sole writer

Context: the inbox surfaces things that need a human — failed tasks, blocked tasks, stale worktrees, draft proposals — as derived rows (`derived-inbox.ts`, duplicated by hand in `ui/server/derivedInbox.ts`). Until now the `ui/` package was strictly read-only: a standalone `@mars/ui` Vite SPA + Bun server reading `.mars/mars.db` directly, importing zero orchestrator code, with no path to mutate task state. Recovering a failed/blocked/killed task meant dropping to the CLI (`mars restart`/`unblock`/`purge`). Separately, tasks SIGKILL'd with the daemon were stamped `failureSignature: 'daemon-killed'` but only string-recoverable, with no surfaced affordance to requeue them. The user wanted each alert to compose its own recovery menu — one entity per known error bundling what it is, how it's triggered, and how to recover.

Decision: introduce an error-kind registry — `orchestrator/src/mastra/lib/error-kinds.ts` — as the single source of truth for "what can I do about this?". Each `ErrorKind` is one entity bundling `{ kind, rowKind, trigger, recipe, recoveryActions }`. Keys are a closed, machine-readable const set (`ERROR_KIND_IDS` + an `isErrorKindId` guard) so no consumer can invent an off-list key. `recoveryActions` are declarative descriptors `{ id, label, op, needsConfirm? }` — data, never functions — so they serialise to the browser as-is. `errorKindForRow(rowKind, failureSignature)` resolves a row to its kind, fanning a `failed-task` carrying the daemon-killed signature out to its own requeue-framed `daemon-killed` kind rather than the generic failure menu. The orchestrator owns the registry and the behaviour behind every `op`; the daemon's existing loopback HTTP server (127.0.0.1, OS-assigned port published to `.mars/http.port`) serves `GET /error-kinds` plus `POST /actions/:op/:id` (restart/unblock/purge/prune-worktree) and `POST /actions/restart-daemon`. The read-only UI gains exactly one write path: it reads `.mars/http.port`, fetches the registry over the wire, attaches `actions` to each row by kind, and proxies clicks to the daemon. The daemon stays the single writer; the UI imports no orchestrator code.

Two alternative sharing models were designed and rejected (recorded so they are not re-suggested):

- UI imports the orchestrator registry directly: rejected because `@mars/ui` is a deliberately standalone package that imports zero orchestrator code today; a direct import drags orchestrator's transitive deps (libsql, context resolution) into the UI build and couples the two packages across a boundary the codebase keeps clean.

- A new shared workspace package both sides import: rejected as disproportionate — the monorepo has no workspace-package seam today, and introducing one to share a small frozen data table is a larger, longer-lived change than the problem warrants.

Why: the registry is pure, frozen, dependency-free data, and the daemon already runs a loopback HTTP server and already publishes a port file slot. Serving the registry and the action verbs over that existing channel is the smallest change that (a) keeps one source of truth in the orchestrator, (b) keeps the UI a standalone renderer of descriptors it is handed, and (c) keeps the daemon the only process that writes task state — preserving the read-only-UI invariant in spirit (the UI still mutates nothing itself; it asks the daemon to). Keying recovery on a resolved error-kind rather than the raw row kind is what lets one row kind (`failed-task`) carry different menus by cause, which is the whole point of the feature.

Cost: the UI's "read-only" property is now nuanced — it holds no local writes, but it can drive daemon-side mutation, so the invariant is "single writer is the daemon", not "the UI cannot cause writes". The error-kind taxonomy is mirrored in two places: the registry keys live in the orchestrator, and the row→kind resolution (the `daemon-killed` signature literal, `resolveErrorKind`) is re-implemented locally in `ui/server/derivedInbox.ts` so the UI need not import orchestrator code — the same hand-mirroring already accepted for `derived-inbox.ts`. Drift between the two copies of the daemon-killed signature literal is guarded only by a comment and tests, not the type system. The daemon-killed case is alert-only by deliberate choice: daemon start raises one inbox alert per killed task and never auto-requeues, trading "no lost work without a click" for explicit operator control. `restart-daemon` is a genuine process-lifecycle action (re-exec via `resolveLaunchCommand` + detached spawn, then SIGTERM self) exposed from a button — heavier and riskier than the per-task verbs, accepted because the daemon-killed alert is where an operator most plausibly wants it.
