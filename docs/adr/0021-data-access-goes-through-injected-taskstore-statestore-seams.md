# Data access goes through injected TaskStore/StateStore seams; raw libsql handle never exported

Context: orchestrator/src/mastra/queue.ts exports getClient() (a libsql Client singleton) and initQueue() (an idempotent migration runner: CREATE TABLE IF NOT EXISTS + PRAGMA table_info + additive ALTER backfills) alongside ~30 typed domain functions. Seven live modules (lib/origin.ts, lib/origin-timeline.ts, lib/reflect-query.ts, lib/reflect-signals.ts, lib/deep-reflect-query.ts, blocker-resolution.ts, queue-retry.ts) bypass the domain functions and hand-roll SQL on the raw client. Separately, proposals.ts and lib/inbox.ts each independently re-declare a private getClient()/clientSingleton against state.db -- the same connection-lifecycle implementation written three times. The raw handle is a shallow seam: its interface (a libsql Client) is as complex as the database it fronts, so every caller must learn the schema rather than the domain, and any test that touches tx.execute is testing past the seam.

Decision: introduce two deep modules, TaskStore (over .mars/queue.db) and StateStore (over .mars/state.db). Each keeps the existing typed domain methods as the front door and adds a generic, parameterised Stmt side door -- query (read-only, enforced by libsql 'read' mode), execute (single ad-hoc write), and atomic(fn) (callback-scoped multi-statement transaction). The libsql Transaction never crosses the seam: atomic inverts control (you give a callback, you do not get a handle) and the scope it passes exposes only query/execute, is non-nestable, and is revoked once the callback settles. Schema migration moves behind the store (lazy, memoised) so callers stop hand-sequencing initQueue(). The store is created once at the composition root via constructor injection of a libsql Client (file: for production, :memory: for tests); getClient()/initQueue() are removed from queue.ts's public surface in the same change, and all twelve hand-rolling/duplicating call sites are migrated in that one hard cut (no keep-both-for-now, per CLAUDE.md).

Two alternative interface shapes were designed and rejected with load-bearing reasons (recorded so future architecture reviews do not re-suggest them):

- Verb-collapse design (a single tx() handle exposing low-level domain verbs; the ~30 domain functions collapse into caller-side compositions): rejected because it relocates read-modify-write policy (claim-if-ready, fix-task dedup) out of the store and back into callers as new shallow modules -- the exact "pure functions extracted but the real bug is in how they are called" friction this work exists to remove. It moves leverage rather than creating it, and fails the deletion test (policy complexity reappears across callers).

- Common-case-only design (four trivial hot methods plus one rigid enqueue; the long tail such as dropTask and reflection inserts explicitly left on the raw client): rejected because it does not close the raw-handle leak -- it leaves a mixed state where some modules still import getClient(), which CLAUDE.md's hard-cut rule forbids.

The chosen design is the only one of the three after which no live module imports the raw libsql handle.

Why: the friction being removed is precisely a set of named modules reaching past a shallow seam. Only an interface that (a) keeps the high-leverage typed methods, (b) gives the irreducibly-ad-hoc callers a contained side door whose escape hatch cannot be widened back into a handle, and (c) is injected (not a hidden global) actually concentrates schema knowledge and transaction correctness in one place while keeping the migration mechanical. Constructor injection at the root is chosen over a module-singleton-with-test-override because it is the purest seam (no hidden global, prod/test selection visible at one site), and the larger diff is acceptable under the project's single-hard-cut rule.

Cost: every data-access call site takes a store parameter threaded from the composition root, so the introducing change is wide (touches the daemon, workflows, CLI, and the twelve direct callers). Domain invariants that are read-modify-write (claim-if-ready, fix-task dedup) ship as thin pure helpers over the atomic scope, co-located with their callers, rather than as store methods -- so the store stays free of policy at the cost of those helpers living outside it. The generic side door admits SQL sprawl across the seven modules; this is bounded by a convention (any query shared by >=2 modules is promoted to a named domain method, not generalised into a query DSL), enforced in review rather than at runtime. ObservabilityStore (the DuckDB span store read by origin-timeline.ts) is explicitly out of scope; conflating it with TaskStore would be a seam bought with a leak.
