# Workflow engine is domain-agnostic with pluggable agent runtimes

Context: the orchestrator currently runs on Mastra, but uses none of its agent primitives — we only use `createWorkflow().then()` chains around `claude -p`. Mastra ships seven `@mastra/*` packages, a SQLite migration story, and an agent runtime we never invoke. Decision: replace Mastra with a small in-house workflow engine that lives in `packages/workflow/` as a standalone TypeScript package with no knowledge of Mars, coding agents, or git worktrees. The engine exposes (1) a DAG step model with Zod-typed inputs/outputs and durable resume from the last completed step, (2) a logger that is part of the engine surface (every step receives a child logger; lifecycle events are logged automatically), and (3) an `AgentRuntime` interface with two reference implementations — `HeadlessRuntime` (spawns `claude -p`, streams JSON events) and `TmuxRuntime` (sends keystrokes to a pane and scrapes output). Steps depend on `AgentRuntime`, not on a specific binary. Storage is pluggable through a `WorkflowStore` interface; the orchestrator implements it against `.mars/queue.db`, but the engine ships a `Sqlite3Store` reference impl that works against any path. Why: the framework is the leverage — a standalone package can be consumed by other local-CLI agent tools, and forcing the engine to know nothing about Mars keeps the abstraction honest. Logging-by-design means consumers don't bolt on observability later; the engine's contract is "steps log, the engine streams." The runtime split lets the same workflow run unattended (CI, daemon) or interactively (Tmux pane the user can watch and interrupt) without changing step code. Cost: orchestrator-specific concerns — daemon semaphores, fix-task fallout, scorers, recovery recipes — must live in the consumer, not in the engine. The engine surface is the contract; breaking it bumps a major version.
