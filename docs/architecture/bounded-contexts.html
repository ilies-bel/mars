Mars Framework — Bounded Contexts & DDD Strategy

Imposing a coherent domain model over the current organically-grown orchestrator. Every entity attached to an arc; no stranded work, enforced by construction.
strategy draft · grounded in CONTEXT.md glossary + ADR-0001…0051 · one lib (@mars/mars) · workflows scaffolded into .mars/workflows/

The thesis

Mars is not missing a domain model — it has a deep one buried in 50+ ADRs, a rich glossary, and a 2,400-line queue.ts. What it lacks is a bounded-context map that makes its invariants enforced by construction at the aggregate level rather than scattered across functions, stores, subscribers, and raise-paths. The symptom that triggered this: a context-exhausted follow-up (MARS-21175626) that renders as "No origin recorded" because it was written with origin_id = self before the fix landed — an entity stranded from its arc.

Core invariant (this strategy's reason to exist): every action is attached to an arc; every arc has an origin task; no mutation may create a stranded entity. Enforced by an app-level aggregate root (the only writer), assertArcInvariant() on every path, with the raw DB client unexported.

The stranding bug, concretely

Planning

Shape an idea into runnable work.

  • Tree = Proposal + its Arcs
  • Proposal (draft → prd-ready → sliced)
  • slice → emits Arcs into Execution
  • a sliced Arc carries the Tree's proposalId

Execution core

Run work to done.

  • Arc (origin Action + continuations)
  • Action {kind: task|fix|diagnose|write}
  • WorkflowRun (setup→code→verify→merge)
  • every Action attached to an Arc
  • every Arc has an origin Action
  • Blocker edges: no Idea→Task cycle (ADR-0015)

Recovery

Last automatic shot at a failure.

  • Recovery Action (kind=fix)
  • Probe (kind=diagnose)
  • recovery is a leaf node (ADR-0040)
  • fix carries by-construction origin edge (ADR-0049)
  • exactly one recovery per origin failure

Operator Attention

Everything needing a human.

  • Action Queue = Alerts + Drafts
  • Alert (arc-rooted: goal→reason→technical)
  • pure projection of entity state (ADR-0048)
  • arc key = resolved origin_id (ADR-0051)
  • an Alert clears only by mutating its entity

Observability

Did the harness get better?

  • KPI vector (ADR-0038, four KPIs)
  • Step span / trace events
  • Reflection (arc post-mortem → draft proposals)
  • cost denominated per completed Arc

Provisioning

Get a repo onto Mars.

  • Project registry
  • Supervisor render (stack detect)
  • Workflow scaffold (.mars/workflows/*.js)
  • single init; every prompt has a flag
  • scaffolded workflows are user-owned (no overwrite)

Shared kernel (no upstream deps)

  • Mars id / Bare id — identity (ADR-0039)
  • Bus event / Outbox / Subscriber — delivery (ADR-0030/31)
  • Failure kind — signature → human reason + recipe + actions (ADR-0042)
  • Status transition — the one funnel (Transition seam)

Target · Layer view

One library, @mars/mars. Three logical layers inside it, with strict dependency direction enforced by an arch-test (upper imports lower only — never upward). The ADR-0047 eight-rung package ladder is retired as too fine-grained. The only thing crossing the install boundary into the consumer repo is scaffolded workflow JS.

Adapters operator-facing

imports ↓ Domain (and Engine via Domain only)
  • daemon — dispatch loop, semaphores, HTTP, subscribers
  • CLI — the mars command seam (ADR-0023)
  • UI — read-only viewer
  • TUI — new terminal surface
  • skills — Claude Code /mars:*
All five call the Application-Service layer (use-cases) — no surface re-implements projection or invariant logic.

Domain process-free brain

imports ↓ Engine only · NO process / HTTP / TTY in this layer
  • Aggregates: Arc (root writer), Tree, Proposal, Action Queue, Alert
  • Invariants: assertArcInvariant, leaf-node rule, kind-routing
  • Stores: TaskStore / StateStore (raw client unexported)
  • Events: outbox publish/subscribe primitives + Mars subscribers
  • Application services: use-cases that adapters call

Engine mechanics

imports nothing upward — knows nothing of tasks/arcs/recovery
  • workflow runtime — defineWorkflow, ctx.step, checkpoint-resume
  • agent runtime — runClaudeCode + ClaudeEvent (pulled out of git.ts)
  • claude-session — PTY control
  • git-worktree — worktree / verify / merge primitives
  • step primitives exported for scaffolded workflows: setupWorktree, runAgent, verify, merge

The workflow extension boundary

Custom workflows are sandboxed plain-JS with declared steps. They compose engine step primitives and write to the DB only through injected arc services — so the no-stranded-entity invariant holds for custom flows too.

// .mars/workflows/implement.js  — scaffolded by `mars init`, user-owned
import { defineWorkflow, setupWorktree, runAgent, verify, merge } from 'mars'

export default defineWorkflow({
  id: 'implement',
  kind: 'task',                          // which Action kind this flow handles
  steps: [setupWorktree, runAgent, verify, merge],
  // DB access ONLY via ctx.arc (injected) — raw store is NOT in scope
})
mars init→ scaffold .mars/workflows/*.js→ daemon boot: dynamic import + register→ mars daemon reload: re-read
Scaffolded workflows are Hybrid files (glossary). mars update never silently overwrites them — it shows a diff against the new template for the user to merge.

Arch-test dependency rule (build-guard)

// fails the build if any import crosses a layer upward
adapters → domain → engine        // allowed
domain   → adapters               // FORBIDDEN
engine   → domain | adapters      // FORBIDDEN
domain   → process | http | tty   // FORBIDDEN (domain is process-free)

Aggregates, entities & their methods

The write model. The Arc aggregate root is the single thing permitted to create work; the legacy free functions (enqueueTask, upsertFixTask, enqueueFollowUpOnce) become private members. TypeScript keeps the raw client unexported; assertArcInvariant() runs on every write path.

Arc — aggregate root (Execution)

identity
origin_id (the originating Action's id)
holds
origin Action + every recovery / follow-up Action sharing its origin_id
invariant
non-empty (always ≥ origin); origin Action's origin_id === id; recovery Actions are leaves
// the ONLY task/arc writer in the system
class Arc {
  static createOrigin(spec: ActionSpec): Arc          // replaces enqueueTask (origin path)
  addContinuation(spec, { inheritArc: true }): Action   // replaces --blocked-by / followup; origin_id inherited
  spawnRecovery(failed: Action, kind: 'fix'|'diagnose'): Action  // replaces upsertFixTask; by-construction edge
  transition(action: Action, to: Status): void          // the one status funnel
  addBlocker(from: Action, to: Action): void             // asserts not-recovery-edge (ADR-0040)
  drop(): void                                           // cascades the whole arc (ADR-0049)
  status(): ArcStatus                                    // stateless rollup (existing arcStatus)
  private assertArcInvariant(action): void           // runs on every write; no stranded entity
}

Action — entity within Arc

type ActionKind = 'task'|'fix'|'diagnose'|'write'
Action {
  id; arcId(origin_id); kind; spec; status
  fixForTaskId   // non-null iff kind=fix
  selectsWorkflow(): WorkflowId  // kind-routed
}

Tree — aggregate (Planning)

Tree {
  proposal: Proposal | null   // null ⇒ standalone
  arcs(): Arc[]               // all slices
  slice(): Arc[]              // Proposal → Arcs
}
// standalone `task add` = 1-Arc Tree (proposal=null)

Proposal — aggregate (Planning)

Proposal {
  status: draft|prd-ready|sliced|dismissed
  promote(); reject(); setField(); markSliced()
  blockers(): Proposal[]   // ADR-0008 separate junction
}

Action Queue — aggregate (Operator Attention)

ActionQueue {
  // pure projection — no close verbs (ADR-0048)
  alerts(): Alert[]          // failed/blocked/stale
  drafts(): Proposal[]       // draft proposals
  // rows clear ONLY when entity transitions
}

Alert — arc-rooted read aggregate (the new one)

// composed from an Arc + its failure-kind; the operator-facing hierarchy
Alert {
  arcId                                  // resolved origin_id (ADR-0051)
  goal: string                           // origin Action's intent, plain summary
  reason: string                         // FailureKind.humanReason — clear English, no jargon
  technical: {                           // drill-down, deeper in the hierarchy
    failedAction: { id, kind, worktree }
    signature: FailureSignature
    traceTail: TraceEvent[]
    descendants: Action[]                // fix/diagnose attempts
  }
  clearsBy: 'mutate the underlying entity'  // never a dismiss gesture
}
This directly satisfies your spec: "Alert should aggregate a full failed arc and expose the information in a hierarchy relevant to the user: the goal of the original task, a clear English message of why it failed, then more technical details after."

Application-service layer (the shared seam)

// every adapter (CLI/daemon-HTTP/TUI/skills) calls THESE — never the store directly
appService = {
  // Planning
  proposals.{create, promote, reject, slice}
  trees.{list, show}
  // Execution
  arcs.{createOrigin, addContinuation, list, show, status}
  actions.{transition, block, unblock}
  // Recovery
  recovery.{spawn, diagnose}
  // Operator Attention
  alerts.{list, show}            // arc-rooted; goal→reason→technical
  actionQueue.{view}            // alerts + drafts, pure projection
  // Observability
  kpis.{snapshot, window}; reflect.{run, arcReflect}
  // Provisioning
  projects.{add, list, remove}; workflows.{list, scaffold, validate, reload}
}
